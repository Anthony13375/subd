# Домашнее задание к занятию "`Базы данных, их типы`" - `Герасимов Антон`

#### Задание 1. СУБД
#### Кейс
Крупная строительная компания, которая также занимается проектированием и девелопментом, решила создать правильную архитектуру для работы с данными. Ниже представлены задачи, которые необходимо решить для каждой предметной области.

Какие типы СУБД, на ваш взгляд, лучше всего подойдут для решения этих задач и почему?

1.1. Бюджетирование проектов с дальнейшим формированием финансовых аналитических отчётов и прогнозирования рисков. СУБД должна гарантировать целостность и чёткую структуру данных.

1.1.* Хеширование стало занимать длительно время, какое API можно использовать для ускорения работы?

1.2. Под каждый девелоперский проект создаётся отдельный лендинг, и все данные по лидам стекаются в CRM к маркетологам и менеджерам по продажам. Какой тип СУБД лучше использовать для лендингов и для CRM? СУБД должны быть гибкими и быстрыми.

1.2.* Можно ли эту задачу закрыть одной СУБД? И если да, то какой именно СУБД и какой реализацией?

1.3. Отдел контроля качества решил создать базу по корпоративным нормам и правилам, обучающему материалу и так далее, сформированную согласно структуре компании. СУБД должна иметь простую и понятную структуру.

1.3.* Можно ли под эту задачу использовать уже существующую СУБД из задач выше и если да, то как лучше это реализовать?

1.4. Департамент логистики нуждается в решении задач по быстрому формированию маршрутов доставки материалов по объектам и распределению курьеров по маршрутам с доставкой документов. СУБД должна уметь быстро работать со связями.

1.4.* Можно ли к этой СУБД подключить отдел закупок или для них лучше сформировать свою СУБД в связке с СУБД логистов?

1.5.* Можно ли все перечисленные выше задачи решить, используя одну СУБД? Если да, то какую именно?

Приведите ответ в свободной форме.


### Ответ к заданию 1

1. Думаю лучший выбор - это реляционная СУБД, например PostgreSQL. Потому что SQL отлично подходит для сложных аналитических отчетов с джойнами и агрегациями. Прогнозирование рисков часто строится на исторических данных, которые удобно хранить в реляционных таблицах
2. Для лендингов лучше всего подойдёт - документоориентированная NoSQL СУБД. Потому что NoSQL позволяет гибко добавлять и изменять поля без перестройки схемы. Высокая скорость записи и горизонтальная масштабируемость важны для обработки пиковых нагрузок. Для CRM больше подойдёт реляционная СУБД. Потому что CRM - это чёткие сущности с жёсткими связями
3. Здесь в принципе можно выбирать как реляционную СУБД, так и докуменориентированную. Главное требование - это простота и понятность структуры
4. Для логистики подойдёт графовая СУБД. Потому что она создана для эффективного выполнения алгоритмов на графах (поиск кратчайшего пути, оптимизация маршрута с несколькими точками) и работы со сложными, многоуровневыми связями, что неэффективно делать в реляционных БД множественными джойнами

**5. Уведомление клиента и фиксация в биллинге**
* Информирование сторон и бухгалтерское закрытие

**6. Постоперационная обработка** 
* Действия, которые не влияют на успешность основной транзакции, но важны для бизнеса

### Задание 4. Кластеры

Необходимо производить большое количество вычислений при работе с огромным количеством данных, под эту задачу выделено 1000 машин.

На основе какого критерия будете выбирать тип СУБД и какая модель распределённых вычислений здесь справится лучше всего и почему?

Приведите ответ в свободной форме.

#### Ответ к заданию 4

При такой задаче ключевыми критериями становятся масштабируемость, производительность, тип данных и характер рабочих нагрузок, а также требования к отказоустойчивости и интеграции с существующей инфраструктурой.

Подходящие модели распределённых вычислений:
**1. MapReduce.** Модель разделяет данные на части, обрабатывает каждую часть параллельно на отдельном узле, а затем объединяет результаты. Подходит для пакетной обработки больших объёмов данных. Реализована в Apache Hadoop и других системах.
* Преимущества: устойчивость к сбоям узлов, возможность динамического распределения задач по кластеру.
* Недостатки: менее эффективна для интерактивных запросов и обработки в реальном времени.
**2. Apache Spark.** Использует концепцию RDD (Resilient Distributed Dataset) — неизменяемых распределённых наборов данных, которые обрабатываются параллельно. Поддерживает «ленивые вычисления», что позволяет выполнять только необходимые вычисления. Подходит для сложных ETL-задач, машинного обучения и интерактивных аналитических запросов.
* Преимущества: широкая поддержка форматов данных (Parquet, JSON, ORC и др.), интеграция с фреймворками машинного обучения.
* Недостатки: менее удобен для эластичных интерактивных нагрузок по сравнению с некоторыми другими системами.
**3. Векторизованное выполнение запросов.** Используется в системах вроде ClickHouse. Операции выполняются не на отдельных значениях, а на массивах данных, что значительно ускоряет обработку. Оптимизировано для аналитических запросов в реальном времени.

Чаще оптимальным решением становится гибридный подход: сочетание нескольких СУБД и моделей вычислений для разных типов задач.
